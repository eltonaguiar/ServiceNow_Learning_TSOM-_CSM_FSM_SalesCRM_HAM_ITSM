Purpose

IT Operations Management (ITOM) is the set of ServiceNow applications that help IT monitor, discover, and manage infrastructure and services. It includes Discovery, Event Management, Service Mapping, Orchestration, and Cloud Management. ITOM’s goal is proactive operations — detecting issues before users report them, and automating routine infrastructure tasks.

ITOM sits on top of the CMDB. Discovery populates CIs; Event Management consumes alerts from monitoring tools; Service Mapping connects CIs to business services; Orchestration automates remediation.

Business Rule: Create Incident from High Severity Alert

(function rule(current, previous) {
    if (current.operation() == 'insert' && current.severity == '1') { // Critical
        var gr = new GlideRecord('incident');
        gr.short_description = 'Critical alert: ' + current.node;
        gr.description = current.message;
        gr.priority = '1';
        gr.assignment_group = 'NOC';
        gr.cmdb_ci = current.ci;
        gr.insert();
    }
})(current, previous);

Common Mistakes

Mistake Symptom Fix
No event rules configured Events arrive but never become alerts Create event rules for each monitoring tool
No correlation rules Hundreds of alerts for one outage Configure alert correlation by node or CI
MID Server can’t reach network Discovery returns no CIs Place a MID Server cluster in each network zone (per firewall boundary, not per subnet)
One standalone MID per subnet Many under-used VMs, no HA, config drift across IP ranges Two or more MIDs per zone in a load-balancing cluster with identical ranges/capabilities
Not de-duplicating events Alert storm during outage Use event rules with de-duplication (node + resource + type)
Discovery without credentials Incomplete CI data Configure Discovery credentials per OS/application
Alerts never become incidents NOC never sees the alert Business rule or correlation rule creates incident from critical alerts

Deep Dive: Event Management → Incident

The flow

  1. Monitoring tool detects an issue (server down, disk full, service stopped)
  2. Event sent to ServiceNow via REST, SNMP, or email → em_event
  3. Event Rule evaluates the event → creates em_alert
  4. Alert Correlation groups related alerts → one alert represents one issue
  5. Business Rule or auto-closure → creates incident
  6. NOC agent works the incident → resolves → closes alert

Severity mapping

Event Severity Alert Severity Incident Priority
1 (Critical) Critical P1
2 (Major) Major P2
3 (Minor) Minor P3
4 (Warning) Warning P4
5 (Clear) Clear Auto-close

SLAs, Dashboards & Workspaces

SLA Support

ITOM alerting and incident handling use ServiceNow SLAs defined on task_sla, which tracks SLA records against task-based tables (incident, em_alert, task).

SLA Area What It Tracks Typical Target
Alert acknowledgment Time from alert creation to In Progress state < 15 minutes
Alert resolution Time from alert creation to Resolved state < 4 hours
Incident response Time from incident creation to first agent action < 30 minutes
Incident resolution Time from incident creation to Resolved state < 4 hours

MTTD (Mean Time to Detect) — measured from the triggering event in em_event until an alert exists in em_alert. Typical target: under 5 minutes.

MTTR (Mean Time to Resolve) — measured from alert creation until the related incident reaches Resolved. Typical target: under 30 minutes for P1/P2, under 4 hours for P3/P4.

Use task_sla to:

  • Attach SLA definitions to incidents created from critical alerts (severity = 1)
  • Track breach risk with stage, has_breached, and business_duration fields
  • Escalate tasks when an SLA stage approaches its threshold

End-to-End ITOM Design (Real-World)

This section is the architecture view: how a production ITOM stack actually fits together, and the design choices that separate a working deployment from a fragile one.

The layered stack

Layer Component Purpose
Discovery MID Server, Patterns, Schedules, Probes/Sensors, ECC Queue Find CIs and relationships across on-prem, cloud, mainframe
CMDB CI classes, Relationships, Health, Data Policies Single source of truth for configuration items

Event Management Event Rules, Noise Reduction, Alert Correlation, AIOps Turn raw monitoring events into actionable alerts

Reference topology

  • One MID Server cluster per network zone — place them per routed, firewall-isolated zone (data center core, DMZ, cloud VPC/VNet, restricted PCI segment), not per subnet. Discovery should not cross a firewall to reach targets; a routed subnet inside a zone does not need its own MID Server.
  • One MID Server cluster per cloud region for cloud discovery.
  • Cluster “like” MID Servers (groups of 2–4, identical capabilities and IP ranges) and prefer load-balanced clusters for Discovery — work is shared continuously, so a lost member’s jobs are picked up without a manual step. A failover cluster works too, but its members sit mostly idle until needed.
  • Dedicate MID Servers to a single purpose: keep Discovery and Event Management on separate MID Servers. Service Mapping and Discovery can share a MID Server only if their schedules do not run concurrently.
  • Keep LDAP, export sets, and JDBC data sources off clusters entirely — ServiceNow’s own cluster documentation says these should use dedicated, non-clustered MIDs, because a failover restarts the ECC job from the beginning and can duplicate data.
  • Stagger discovery schedules — never let every schedule fire at the same time.

Real-world sizing data point: customers running clusters of 4 MID Servers (4 vCPU @ 2 GHz+, 32 GB RAM, 80–100 GB disk, 25–100 threads at ~0.5 GB/thread) have discovered roughly 5,000 servers in under two hours.

MID Server placement — network zones, not subnets

A very common design mistake is reading the platform’s IP range selection mechanism as an instruction to deploy one MID Server per individual subnet. It is not. ServiceNow’s guidance is a cluster per network zone / security boundary, with at least two members per zone.

What “1 MID Server per subnet” gets wrong

Architectural dimension 1 MID per subnet ServiceNow best practice Impact of the subnet model
Network placement One host in every subnet One cluster per isolated network zone (data center, DMZ, cloud VPC, firewalled segment), placed close to targets Over-provisioned. If internal subnets can route to a shared zone, per-subnet MIDs are infrastructure with no discovery benefit
High availability Single node per subnet — a 100% single point of failure At least 2 MIDs per zone in a load-balancing cluster High risk. Patching, an upgrade, or a host crash stops all ServiceNow activity in that subnet; if every member of a cluster is down, the discovery is cancelled
Workload separation One MID carries Discovery, integrations, and events for its subnet Separate clusters by workload (dedicated Discovery vs Integration/Event) Contention. A heavy scan starves time-sensitive integrations or trap/event traffic on a shared agent
Host and resource sizing Many small, under-utilised VMs in quiet subnets One MID per dedicated host, tuned past OOTB defaults (raise threads.max above 25, JVM heap to 2–4 GB) Operational overhead. Dozens of individual VMs means dozens of OS patch cycles, monitoring targets, and upgrade windows
IP ranges, capabilities, applications Manually or auto-assigned, mapped 1:1 to each subnet Identical Supported Applications, IP Ranges, and Capabilities on every member of a cluster Configuration drift. Unique range/capability rules on many single servers is the most common source of “work went to the wrong MID” tickets

The recommended architecture

  1. Group subnets by security zone. Identify which subnets share firewall rules and routing — standard internal LAN/VLANs, a restricted DMZ, an AWS/Azure VPC.
  2. Deploy a cluster of 2+ per zone. Minimum two members on separate hosts (or separate availability zones). Configure identical IP ranges, capabilities, and supported applications on each member — that is the documented prerequisite for a cluster, and it is what lets the platform hand any job to any member.
  3. Split heavy workloads. In busy zones, run separate clusters for Discovery/Service Mapping and for Integrations/Event Management so a scheduled scan never blocks real-time API or alert traffic.
  4. Reserve a standalone MID for exceptions only. An air-gapped or strictly firewalled subnet that cannot route to a zone cluster gets its own MID Server — and if the assets there are business-critical, pair it with a second node anyway.

Two configuration rules people trip over

  • A MID Server may belong to only one cluster. Membership in multiple load-balancing clusters produces Discovery authentication/timeout errors (KB0997595) — the single most common MID cluster misconfiguration.
  • IP range auto-assignment is a selection mechanism, not a sizing mandate. ServiceNow’s “MID Server IP range auto-assignment” feature assigns a qualified MID Server to a subnet by that subnet’s IP address range — it exists so the platform can route a scan to an agent that can reach the target. One cluster covering a whole zone’s ranges satisfies it just as well as one MID per /24, and it keeps the range table maintainable.

Interview framing: “I don’t put a MID in every subnet. I place a load-balanced cluster of two or more per network zone — DMZ, internal, each cloud VPC — with identical capabilities and IP ranges on every member, and separate clusters for Discovery versus integrations so scans never starve real-time traffic. A standalone MID only survives as an exception for genuinely air-gapped segments.”

Placement and identity

  • Install the MID Server on a local drive in a folder name with no spaces (e.g. C:\ServiceNow\MID_Server_Agent).
  • In production, install one MID Server per host.

Why one MID Server per host in production

Reason What happens if you co-locate
Resource contention Two MID Servers on one host share CPU, memory, and disk I/O. Discovery jobs are probe-heavy and bursty; one server’s GC pauses or thread spikes starve the other. You get slower scans, timeouts, and intermittent failures that are hard to attribute.
Scheduling collisions Discovery schedules fire independently. Two servers on one host can launch heavy jobs at the same moment, doubling I/O and network load on the host exactly when capacity is least available.
Maintenance windows Patching or rebooting one MID Server now takes down discovery for all the targets assigned to both servers on that host. One-per-host means you can restart or upgrade one MID without affecting the other.
Failure isolation If a misbehaving discovery leaks memory or pegs CPU on one MID, a co-located MID suffers collateral damage. One-per-host contains the blast radius to a single MID’s target set.
Log clarity agent0.log.0, wrapper.txt, and ECC Queue entries mix when two agents write from the same host. Debugging becomes guesswork about which log line belongs to which MID.
Capacity planning The MID Server estimator sizes threads and heap per MID. With one-per-host you know exactly what each box can take. With co-located agents you’re guessing at split-half allocations.

When the rule relaxes: A single host can run multiple MID Servers only in non-production (sandbox, dev) where load is light and failure carries no consequence. Even then, give each its own folder, service account, and port range so they do not collide.

Windows 11 — strongly advised against, and effectively blocked

A company can force a MID Server onto Windows 11 only with a manual ZIP-file install (the .msi installer refuses, reporting “This package required minimum OS version: Windows Server 12 or greater”). It is strongly advised against:

  • Not a supported OS. The supported Windows list is Windows Server 2012/2016/2019/2022/2025. Windows 10 and 11 are desktop/client operating systems and are explicitly unsupported — the docs state “Windows 10 is unsupported,” and Windows 11 is not on the supported list at all.
  • It is a server product. The MID Server is designed to run as an unattended background service 24/7 (discovery, orchestration, Service Mapping). Windows 11’s servicing, power management, and update behavior are built for interactive desktop use, not server workloads.
  • No support path. If a Windows 11 MID Server fails, ServiceNow support will point you to a supported OS first — you lose the ability to open a meaningful MID-related support case.
  • Community-confirmed: installers fail on Windows 10/11 with the server-version requirement error; even the ZIP workaround is officially unsupported.

Bottom line: run production MID Servers on Windows Server (or supported Linux), inside a VM if you like — never on Windows 11. If your standard desktop image is Windows 11, that image is not a MID Server host; provision a Windows Server VM instead.

  • Prefer a Windows MID Server — it can perform Discovery and Automation on both Windows and Unix, whereas a Linux MID Server can only act on Unix.
  • Run under a dedicated service account, not SYSTEM or root.

Capabilities and load balancing

  • Give each MID Server capability tags (discovery, servicemapping, cloud, event management) and point schedules at the matching capability.
  • For capacity, deploy multiple MID Servers and let the platform load-balance across them. Load-balanced clusters beat failover clusters for horizontal discovery: work is shared continuously and a lost node’s work is naturally picked up.
  • Monitor with MID Server → Dashboard after every tuning change; watch queue depth, ECC queue backlog, and resource utilisation.

The MID Server estimator

MID Server Load Balancing — Setup, Capacity Math, and Validation

This is the operational detail behind “load-balanced clusters beat failover clusters.” Here is exactly where it is configured, the arithmetic that decides whether the setup is adequate, and how to prove it on a pilot before committing the full estate.

1. How and where to set it up (exact steps)

Load balancing in ServiceNow is delivered through MID Server clusters, not through a hardware load balancer in front of the agents. (Discovery is outbound from the MID Server; you are balancing jobs across agents, not inbound traffic.)

Step 1 — Prerequisites

  • All MID Servers that will share load must have similar hardware and configuration (same CPU/RAM/threads). A weak node drags the whole cluster.
  • All members must carry the same Supported Applications, IP Ranges, and Capabilities — ServiceNow’s documented prerequisite for a cluster (“Ensure that all MID Servers in the cluster have the same capabilities”). A member with a narrower IP range silently excludes its targets from the pool.
  • Each MID Server must be assigned the capability the work needs (discovery, servicemapping, etc.).
  • A MID Server may belong to only one load-balancing cluster. Putting one MID in multiple load-balancing clusters causes Discovery authentication/timeout errors (ServiceNow KB0997595) — this is the single most common misconfiguration.
  • Do not cluster LDAP, export sets, or JDBC data sources. The docs direct these to dedicated, non-clustered MIDs: on failover the surviving member restarts the ECC job from the beginning, which can return duplicate rows.

Two things that are not load balancing. Capabilities (discovery, servicemapping) only select which MIDs are eligible for a job — they do not distribute work. A hardware/software load balancer in front of the agents does not help either: Discovery traffic is outbound from the MID to targets, so there are no inbound connections to balance. Distribution happens through the cluster record and the platform’s MID Server Cluster Management business rule.

Step 2 — Create the cluster

  1. Navigate to MID Server → Clusters (table ecc_agent_cluster).
  2. Click New.
  3. Name the cluster (e.g., DC1-Discovery-LB).
  4. Set the cluster type = Load balancing (the alternative, Failover, uses a fixed order and does not share load).
  5. Save.

Step 3 — Add MID Servers as members

  • On each MID Server record (MID Server → Servers), set its Cluster field to the cluster you created (this populates cluster_id).
  • Alternatively, use the cluster record’s member related list to add MID Servers.
  • Validate each MID Server afterwards (status Up, version matching the instance).

Step 4 — Point work at the cluster / capability

  • On each Discovery Schedule (Discovery → Discovery Schedules), the MID Server field accepts the cluster (or multiple MID Servers). With a load-balancing cluster, the platform distributes the ECC jobs across members automatically.
  • Use Discovery behaviors (c_DiscoveryBehaviors) when different network segments must be scanned by different MID Servers — a behavior assigns tasks to specific MID Servers on the same or different IP segments.
  • For Service Mapping, assign the cluster/capability the same way.

Step 5 — Verify

  • MID Server → Dashboards → MID Server Health: all members Up, Validated, same version, and each showing Pending/Processing jobs.
  • Run a small discovery and confirm the ECC Queue jobs are spread across the members (each MID processes a share), not all queued on one.

2. The capacity math — how many MID Servers, how many threads

There is no magic formula, but there is a defensible calculation you should run and then confirm empirically.

A. Establish per-MID throughput from a pilot (do not guess it). Run one MID Server against a representative sample and measure:

R = targets completed per hour      (from Discovery Status duration + target count)
P = average concurrent probes       (from Statistics (3h) on the MID form)

R is your throughput per MID Server for that mix of OSes/protocols.

B. Size the cluster for the window.

Required MID Servers = ceil( TotalTargets / (R × DiscoveryWindowHours) / TargetUtilisation )
  • TargetUtilisation = the fraction of a MID’s capacity you are willing to use, e.g. 0.60–0.70. Never plan to run a cluster at 100% — a burst, a slow subnet, or a node outage has nowhere to go.
  • Example: 20,000 targets, R = 1,000/hr, window = 8 h → raw need = 20,000 / (1,000 × 8) = 2.5 MIDs. At 0.65 utilisation → 2.5 / 0.65 ≈ 3.8 → 4 MIDs.

C. Size threads and memory per MID.

Concurrent probes needed = (TotalTargets / DiscoveryWindowSeconds) × AvgProbesPerTarget
Per-MID threads        = Concurrent probes needed / NumberOfMIDs
  • threads.max (config.xml) caps concurrent probes per MID. Default 25.
  • Frequent/continuous discovery at 25 threads → ServiceNow guidance is to start at 8 CPU cores per MID.
  • JVM heap: 2–4 GB recommended (raise in wrapper-override.conf); keep RAM and CPU at ≤80% at peak.

D. Threshold targets to design against (ServiceNow guidance)

Metric Target Where to read it
CPU <90% average, <95% peak (frequent discovery: <70% avg, <90% peak) — brief 100% spikes are normal MID Server Health / Performance tab
Memory <80% of host RAM and <80% of max JVM heap MID Server Health (Max memory used %)
ECC Queue depth Clears between discovery runs MID Server → ECC Queue
Discovery duration Stable trend, not creeping up run-over-run Discovery → Status
Thread activity No sustained saturation of threads.max Statistics (3 hours) on MID form

3. Reports and dashboards that tell you if the setup is fine

  • MID Server → Dashboards → MID Server Health — the primary panel. Columns: Mean CPU used %, Max memory used %, Pending jobs, Processing jobs, version/validation. The Performance tab trends CPU and memory over 30 days; two built-in reports — Avg Percentage of CPU Used and Avg Percentage of Max Memory Used — quantify drift.
  • MID Server → ECC Queue — input/output depth and age. Look for a rising ready count without matching processing/processed (a read-side problem), or steady growth that never drains (a capacity bottleneck).
  • Discovery → Status — per-run duration, errors, warnings; the throughput and quality record.
  • Statistics (3 hours) related list on the MID Server form — live thread usage.
  • MID Server Resource Threshold Alerts — enable the system properties; the platform samples every 10 minutes, compares averages to thresholds, writes breaches to ecc_agent_issue, and can email/notify. (Default is disabled — turn it on or you fly blind.)
  • Application Insights → Overview — ECC queue graphs (ready/processing/processed) for load-handling and efficiency.

Go/no-go rule: the cluster is “fine” when, across several real runs, CPU stays <90% avg / <95% peak, memory <80% of RAM and heap, the ECC queue clears between runs, discovery duration is stable, and no member is consistently idle or saturated. If any of these fail, add a MID Server or increase threads/heap — in that order.

4. Pilot on a subset first — never run the full batch cold

Test on a small, representative subset first. The ServiceNow checklist itself says “test discovery against sample devices.” Concretely:

  1. Sample ~20–50 targets spanning every OS and protocol in the estate (Windows/WMI, Linux/SSH, network/SNMP, cloud, one Mac if present) — not just the easy ones.
  2. Run the cluster against that sample and capture R, CPU, memory, queue depth, and duration.
  3. Extrapolate with the formula in §2 and compare to thresholds in §2D.
  4. Only if it passes, scale up in stages (e.g., 10% → 25% → 50% → 100% of targets), re-checking the dashboard at each stage.

Why not the full batch: a cold full run on an undersized cluster produces timeouts, partial CIs, and an ECC backlog that can take hours to drain — and it is much harder to diagnose than a failed pilot. The pilot is cheap; the failed full run is not.

MID Server Versions & Instance Upgrades

Yes — MID Servers have their own version

The MID Server ships on a release cycle independent of your ServiceNow instance. You’ll see the version on MID Server → Servers (table ecc_agent) in the Version column, next to the Validated flag. The instance and the MID Server share much of the same Glide Java code, so a version mismatch can break discovery, orchestration, and Service Mapping — not just cosmetically, but functionally:

  • The MID Server may fail to validate against the instance.
  • Commands sent from the instance to the MID Server may not be processed.
  • Data coming back from the MID Server may be rejected.
  • Validation and encryption keychain APIs may not match.

So version alignment is a real operational concern, not a vanity number.

Auto-upgrade: the default path

MID Servers upgrade themselves automatically. When the instance upgrades and a MID Server no longer matches the instance version, automatic upgrade is triggered:

  1. The MID Server downloads the new package from install.service-now.com.
  2. It replaces the old files in-place.
  3. It restarts with the new version.

This happens at the end of every instance upgrade. So in the normal case, you do not manually patch each MID Server when the instance upgrades — the platform handles it.

What you must confirm: auto-upgrade only works if the MID Server can reach install.service-now.com (outbound HTTPS 443). Air-gapped or proxy-locked MIDs can’t download the package and will stay on the old version after the instance moves ahead.

Manual patching: when auto-upgrade can’t run

If a MID Server can’t reach install.service-now.com, you upgrade it manually:

  1. Download the MID Server package (mid.zip) from install.service-now.com for the target version.
  2. On the MID Server host, stop the MID Server service.
  3. Back up config.xml, wrapper-override.conf, and any custom parameters/scripts.
  4. Extract the new package over the existing installation (preserving your config files).
  5. Restart the MID Server service.
  6. Verify on MID Server → Servers: Version matches the instance, Validated = yes, status Up.

There is also a manual upgrade via the MID Server record on the instance for some paths — check MID Server → Servers → [MID] for an upgrade option where available.

Instance upgrade procedure — where MIDs fit

Phase Action
Before instance upgrade Note current MID Server versions; confirm all MIDs are Validated and Up. Freeze new MID installs.
Instance upgrade The instance upgrades first. Auto-upgrade triggers for each MID that can reach install.service-now.com.
After instance upgrade Verify every MID Server’s version matches the new instance version and Validated = yes. Investigate any that didn’t auto-upgrade (network, proxy, disk space).
Remediation Manually patch any lagging MIDs; re-validate. Do not run discovery against a version-mismatched MID.

Don’t run production discovery during the version-mismatch window. Wait until every MID Server reports the matching version and is validated.

Go/no-go checklist for instance upgrades

  • All MID Servers Validated and Up before the instance upgrade begins.
  • Auto-upgrade reachable: each MID host can reach install.service-now.com:443 (or a configured proxy).
  • After the instance upgrade, every MID version matches the instance version.
  • Validated = yes on every MID Server record.
  • No discovery schedules running until the above are true.

Bottom line

  • Yes, MID Servers have versions — tracked independently of the instance.
  • You do not normally patch them manually on instance upgrade: auto-upgrade handles it.
  • But you must verify — auto-upgrade fails silently on air-gapped or proxy-blocked MIDs, leaving a version mismatch that breaks discovery. Treat “every MID validated after upgrade” as a hard gate, not an assumption.

Discovery Debugging — Every Potential Problem

Debug top-down. Do not change two things at once.

Step 1 — Is the MID Server healthy?

  • MID Server → Servers: status must be Up, version must match the instance.
  • Your branch may have a MID Server on one version that fails discovery while another succeeds on a different version — run the discovery on a different MID Server to rule that out first.
  • Check the ECC Queue (Discovery > Output and Artifacts > ECC Queue or ECC > Queue). Output records go ready → processing → processed; input records go ready → processing → processed or error. ECC processing errors are the primary starting point for a failed discovery.

Step 2 — Network reachability (run the test FROM the MID Server)

What this step is — and is not. You run these checks on the MID Server host itself (or on a machine on the same network segment as the MID Server), pointed at the target endpoint you expect it to discover. You are proving that the MID Server can reach that target on that port. It is a manual, out-of-band network diagnostic — nothing gets “entered into ServiceNow,” and it does not configure the MID Server. The MID Server’s own Shazzam port-scanner does this during discovery; you are doing it by hand first so you can see the result with your own eyes and rule the network in or out before blaming credentials or patterns.

Where to run each command:

  • If your MID Server runs on Windows Server → open PowerShell/RDP on that host and use Test-NetConnection (native) or download psPing.
  • If your MID Server runs on Linux → SSH into that host and use nc -zv / telnet / nmap.
  • The <ip> is the target (the machine you want discovered), never the MID Server’s own IP.

A failed test here means discovery will fail for that target regardless of credentials — fix the network first.

Protocol Port(s) Run on the MID host, toward the target
WMI (Windows) TCP 135 (+ dynamic RPC range) Windows: Test-NetConnection <target-ip> -Port 135 · Linux: nc -zv <target-ip> 135
SSH (Linux/Unix/Mac) TCP 22 nc -zv <target-ip> 22 or telnet <target-ip> 22
vCenter TCP 443 nc -zv <vcenter-ip> 443 or telnet <vcenter-ip> 443
WBEM (ESXi) TCP 5989 nc -zv <esxi-ip> 5989
SNMP UDP 161 snmpwalk -v2c -c <community> <target-ip> .1.3.6.1.2.1.1 (TCP nc won’t test UDP)
LDAP TCP 389 nc -zv <dc-ip> 389

Tool notes:

  • Test-NetConnection (PowerShell) tests TCP only — it cannot check SNMP/UDP 161; use snmpwalk for that.
  • telnet is fine for a quick TCP check but is often not installed; nc -zv (netcat) or nmap -p 22,135,443,5989 <target> is more reliable and can sweep several ports at once.
  • WMI needs more than 135: after the initial handshake Windows picks a dynamic RPC port (or the RPC range fixed in mid.wmi config). Opening 135 alone with the dynamic range firewalled still breaks WMI — the classic “ping works, discovery fails” case.

Batch ping (L3 only): Test-Connection -ComputerName (Get-Content C:\Data\Computers.txt) -Count 1 proves the host is up — but a successful ping with a blocked port still fails discovery. Always test the actual service port, not just ping.

Then re-run discovery for just that target (Debug mode on the schedule, single-IP scope) and compare: if the manual port test passes but discovery still fails, the problem is past the network — move to Step 3 (credentials) or Step 6 (patterns). That is exactly how this step earns its place: it splits “network problem” from “everything else.”

Step 3 — Credentials

  • Test outside ServiceNow: RDP to a Windows host validates the credential; PowerShell gwmi win32_operatingsystem -computer <ip> -credential '<domain>\<user>' validates WMI directly.
  • Authentication failures → add the correct credential to Discovery → Credentials.
  • WMI/impersonation errors → confirm the domain is in the credential, the MID service account has permission, and the firewall allows WMI.
  • Special characters in passwords can break XML parsing — escape them correctly.

Step 4 — MID Server debug logs

  1. MID Server → Servers → [MID] → Configuration Parameters → New: set mid.log.level = debug.
  2. Reproduce the failure.
  3. Set mid.log.level back to info afterwards (debug logging is heavy).
  4. Grab MID logs from the MID Server record to pull the bundle.
  5. On the host, read ~\agent\logs\agent0.log.0 and wrapper.txt; the presence of agent0.log.0.lck confirms the MID is running.

Look for: Connection timed out, Authentication failed, No WMI connection, Pattern execution error.

Step 5 — Discovery Status detail

  • Discovery → Status → History: open the run and read the Errors/Warnings per phase (Shazzam/port scan, Horizontal Discovery, Vertical Discovery).
  • Common messages:

Step 6 — Patterns

“Pattern must be Active and must include the target CI class” — what that means, and which phase the class is known in

Horizontal discovery has four phases: Scanning → Classification → Identification → Exploration. Patterns only run in the last two — Identification and Exploration. Scanning and Classification still use probes as normal.

Where the CI class is decided:

  • Classification is where the CI class is actually determined. The classification probe returns OS/device detail and that determines the class of the CI (e.g. Windows Server vs Linux vs SNMP device). One classification probe runs per discovered device.
  • Identification — the classifier selects the pattern (via its trigger probes), and the pattern’s identification section confirms the CI class, applies the identification rule, and decides insert vs update. So yes — by Identification the class is effectively known and being applied.
  • Exploration — the pattern’s exploration section uses that CI class to collect attributes and related CIs (disks, NICs, software, processes). Each related CI has its own class too.

So: the class is determined at Classification, then used/confirmed in Identification and Exploration. “Active” means the pattern and its classifier are enabled so the class that Classification produced triggers this pattern; “includes the target CI class” means the pattern’s identification section targets the correct CI class and its identification rule is defined for it — in both the Identification and Exploration sections.

What running a pattern in Debug Mode actually does

Debug Mode executes the pattern against one target, step by step, in isolation — no full discovery, no CMDB write. It runs the real commands/probes on the target via a MID Server and returns the raw output of every step, including the parsed variables each step produced. It is the only way to see the output of the final step of a pattern.

What it shows

  • Per-step command output (the actual SSH/WMI/etc. payload the MID Server ran).
  • The parsed/assigned variables produced at each step (values set via Set Parameter Value operations).
  • Each step’s status: success, or no match / empty — i.e. exactly where a parse, regex, or command fails.
  • The input vs output of the step under test, so you can see the command returned data but the parse didn’t extract it.
  • With Run Again (Debug) on an ECC input record, the script debugger attaches for the pattern’s pre/post scripts.

How to debug with it (exact steps)

  1. Go to Pattern Designer → Discovery Patterns, search/open the pattern.
  2. Open it from Pattern Designer by clicking a link in the Identification or Extension/Exploration section — opening straight from the list view does not expose Debug Mode.
  3. Click the Debug Mode UI action.
  4. Enter the debug parameters:
    • Horizontal (infrastructure) discovery: just a PID + IP address (no entry point).
    • Top-down (Service Mapping) application patterns: requires an Entry Point (Debug Type = Application; infrastructure patterns are horizontal-only and don’t ask).
  5. Run the steps (or the whole pattern) and read the output panel — find the first step that returns empty / no match.
  6. Fix the failing step: correct the command syntax for that OS, the regex/parse, or the credential/protocol mapping. Re-run in Debug Mode until every step returns the expected variable.
  7. For pre/post scripts: Discovery log → ECC Queue → select the input record → Run Again (Debug) attaches the execution context to the script debugger.

Gotchas that waste hours

  • If the host CI State = Absent, pattern debugging will not work for that host. Restore the CI state first.
  • Debug sessions can time out on long patterns (known issue KB3143385) — debug the failing section, not the whole pattern.
  • Debug Mode needs a reachable MID Server with the right capability, same as real discovery — a debuggable pattern still fails if the network/credential is wrong. Debug Mode proves the pattern logic, not the network path (that was Step 2).

The point of Debug Mode vs full discovery: it isolates pattern logic from everything else. If full discovery fails but Debug Mode returns clean output for the same target, the fault is upstream (network/credential/classifier trigger) or downstream (identification rule/coalesce) — not the pattern’s parse steps.

Step 7 — CMDB write, coalesce, and identification rules

Discovery writes need ACL permission on cmdb_ci and derived tables. Duplicates almost always trace to the identification rules (the modern replacement for the old “coalesce” concept), so this is where to look.

“Coalesce” today = the Identification and Reconciliation Engine (IRE). An identification rule applies to a CI class and is built from a single CI identifier plus one or more identifier entries, each with its own priority. IRE tries the entries in priority order to decide “is this an existing CI or a new one?” This is what people still call “coalescing.”

What a “normal” coalesce looks like Out-of-the-box server classes ship with a sensible precedence, roughly:

  • Priority 10: Serial number (or UUID)
  • Priority 20: Name
  • Priority 30: MAC address

Most-strong-and-stable attribute first, weaker fallbacks after. That precedence — not a single attribute — is the “normal” pattern.

Multiple attributes: together vs individually (the key distinction)

You want… How to build it Effect
All must match (stricter) Put multiple criterion attributes in one identifier entry They are ANDed — the entry only matches when every listed attribute is present and matches
A fallback chain (“serial, else name”) Put each attribute in its own identifier entry, ordered by priority IRE tries serial first; if serial is missing, it falls through to the name entry

So serial number + name inside one entry = AND (both required) — that is not a fallback. If you put them in one entry and serial is missing, the entry won’t match at all.

Your example — “serial number, and if missing, a name”: Yes, this is legitimate and is best practice, but you build it as two identifier entries, not one:

  • Entry 1 (priority 10): criterion = Serial number
  • Entry 2 (priority 20): criterion = Name

IRE tries serial first. If serial is absent from the payload, it uses name. This is exactly what priority-ordered entries are for.

The gotcha that trips people up: the fallback fires when the higher-priority attribute is absent/insufficient, not simply when it doesn’t match. If a serial number is present but matches no existing CI, IRE generally creates a new CI using that serial rather than falling through to the name entry — which is usually the right outcome (a serial number is authoritative). Design your expectations around “missing → fall through,” not “no match → fall through.”

Independent vs dependent identifiers

  • Independent — unique on its own (serial number, UUID, MAC). Correct for servers.
  • Dependent — only unique in combination with a related CI (e.g. a network interface identified by MAC plus the server it belongs to). Use for child CIs like NICs, disks.

Other rules that matter

  • Inheritance: a child class inherits the parent’s identification rule unless you define its own — check the effective rule, not just the class you’re looking at.
  • Reconciliation rules are separate from identification: identification answers “same CI?”, reconciliation answers “which data source wins when two disagree?” Don’t conflate them.
  • Audit duplicates with CMDB Health → Duplicate CIs / the IRE dedupe tooling, then fix the rule rather than merging by hand.

Best-practice summary

  1. Prefer strong, stable, unique attributes — serial number, UUID, MAC — as the top-priority entry.
  2. Use name only as a fallback, never as the sole identifier (names duplicate and get renamed).
  3. One attribute-set per identifier entry; use priority to express fallback, AND to express “all must match.”
  4. Use independent identifiers for top-level CIs, dependent for children.
  5. Verify the effective (inherited) rule for the class before blaming detection.
  • The MID Server issue table (ecc_agent_issue) and resource-threshold alerts warn before the MID Server falls over.

Cloud Discovery vs Service Graph Connector (e.g. the AWS SGC)

These are two different tools that both put AWS resources into your CMDB, and people constantly confuse them. They differ in category, mechanism, depth, and governance.

MID Server Required (cloud-capable MID Server) Not required — optional only if firewall/proxy policy forces traffic through one

What each one actually does

  • Cloud Discovery is Discovery. It scans the cloud account, classifies resources, and runs patterns to record CIs and their attributes — the same engine that discovers your on-prem servers. It is the right choice when you need cloud resources to participate in Service Mapping, Dependency Views, and Event Management, or when you need detailed host-level data.
  • Service Graph Connector (SGC) is an integration. It pulls authoritative data from AWS and loads it into the CMDB through IRE with predefined mappings and identification rules. It is the ServiceNow-recommended way to ingest third-party authoritative CMDB data at scale, and it covers a broad set of AWS services and relationships without a MID Server in the default path.

Do they overlap — and can you run both? Yes, they overlap heavily on compute/network/storage, and running both without aligned IRE rules will create duplicate CIs and reconciliation fights. Two sane patterns:

  1. SGC as the CMDB source of truth for AWS inventory + Cloud Discovery only for Service Mapping/operational depth on the hosts you actually map. Align identification rules so both resolve to the same CIs.
  2. Pick one per resource type — e.g. SGC for the broad AWS service inventory, Cloud Discovery for the specific application hosts in a business service.

Rule of thumb: cloud-first CMDB and broad service coverage → SGC. Host-level operations, Service Mapping, alert correlation → Cloud Discovery. Don’t run both blindly against the same resources.

ServiceNow’s own “Choose the Right Cloud Discovery Method” training compares Cloud Discovery, Cloud SGCs, Horizontal Discovery, and ACC — worth referencing when you scope an environment.

Mac (macOS) Discovery — Is It Supported?

Short answer: the MID Server host cannot run on macOS, but a Windows or Linux MID Server can discover Macs as targets. These are two different things, and mixing them up is the usual source of confusion.

Two separate questions

Question Answer
Can the MID Server itself run on macOS? No. The MID Server host OS is Windows Server or Linux (plus legacy Solaris/HP-UX). macOS is not a supported MID Server host.
Can Discovery find Macs as target computers? Yes. Mac (OS/X) is a supported discovery target, discovered over SSH exactly like a Unix/Linux host.

So “Windows is preferable” refers only to where the agent runs, not to whether Macs can be discovered. A Windows Server MID Server discovers Macs perfectly well.

How Mac discovery works

  • Protocol: SSH (port 22). The same SSH credential type used for Unix/Linux.
  • Enable SSH on the target Mac: System Settings → General → Sharing → Remote Login (can be automated via MDM).
  • Credentials: supply Discover’s SSH user; no special privileges are required for the base classification of a Mac.
  • Data collected (via uname, system_profiler, ps, lsof, ifconfig): OS and version, serial number, CPU type/speed/count, RAM, disk volumes and free space, network adapters (IP, MAC, netmask, DHCP), and running processes.
  • Classification:
    • Mac workstations (MacBook, iMac, Mac mini, Mac Pro) → cmdb_ci_computer
    • Mac servers (OS X Server) → cmdb_ci_osx_server
    • Manufacturer assumed Apple; model/serial from system_profiler.

Caveats

  • Macs are end-user devices, not servers, for most estates — discovering them via SSH means every Mac must have Remote Login enabled and reachable, which is often blocked by endpoint security or only enabled via MDM.
  • For large Mac fleets, agent-based collection is usually the better fit: the Agent Client Collector (ACC) supports macOS (Catalina, Big Sur, Monterey, Ventura; x86_64 and Apple Silicon). Horizontal SSH discovery is fine for a handful of Mac servers; ACC scales better across hundreds of laptops.
  • The MID Server does not validate SSH host keys, so for Mac targets (as with any SSH target) prefer key/certificate authentication over passwords and limit sensitive data on the connection.

Bottom line

Keep your MID Servers on Windows Server or Linux. Point them at Macs over SSH to discover them; use ACC for large Mac populations. macOS is a discovery target, never a MID Server host.

Upgrade Strategy & Instance Strategy

When should you upgrade?

  • You need CI classes or features only in newer releases (CSDM updates, new ITOM capabilities).
  • Security vulnerabilities are patched in a newer release.
  • Performance problems are fixed upstream.
  • Your release is leaving the supported window.

“Being on the latest” is not a goal by itself — it is a goal only after your own regression passes. Stay within roughly one major release of current if you want predictable upgrades, and plan at least one upgrade per year.

Upgrade order — always Dev first

  1. Dev instance — upgrade first; run regression against every customization, integration, script and flow.
  2. Test / QA / UAT — upgrade next; test with realistic data volume and business acceptance.
  3. Production — upgrade last, in a maintenance window, with a rollback plan.

Clone order ties into upgrades

  • Always move customizations up the stack (Dev → Test → Prod). Customizations introduced mid-stack get overwritten by the next push from Dev.
  • Before a clone, freeze Dev work and preserve sub-production data you do not want overwritten.
  • Typical production clone: clone Prod down to a sub-production instance with Dev as the target, then rebuild sub-prod data.
  • After any clone, re-check MID Server credentials — the platform flags post-clone MID credential issues automatically.

How many instances should a customer have at minimum?

Instance Purpose Minimum
Dev Development, integration testing 1
Test / QA / UAT Testing and business acceptance 1
Prod Production 1
Minimum total   3

More instances (e.g. adding a separate Sandbox for training) mean more maintenance, more upgrade work, and more clone coordination — so a 3-instance Dev/Test/Prod model is the common minimum, and 4 (adding UAT or Sandbox) is common in larger organisations.

Integration & Credential Hygiene

  • Create a dedicated integration user with least-privilege roles — never use a personal admin account.
  • Store OAuth client secrets and API keys in encrypted storage (ServiceNow encrypted fields, cloud secret managers, environment variables), never in a repo, ticket or chat.
  • Rotate credentials on a schedule and revoke the old ones.
  • Inventory every external credential (Salesforce OAuth, AWS keys, Azure principal, GCP service account) with its storage location and purpose, so rotation and offboarding are deliberate rather than accidental.

The number that matters is alerts per incident, not alert count. A team drowning in 400 alerts that collapse to 4 incidents has a working correlation rule; one generating 40 incidents from 400 alerts does not, and no dashboard redesign fixes that.

AIOps dashboards — which question each one answers

Dashboard Question Caveat
Alert volume / noise Are we suppressing, or just ignoring? Volume falling while MTTD rises means alerts were muted, not fixed
Anomaly (Metric Intelligence) Is this outside normal for this host? Needs a real baseline window; new hosts alert spuriously for days
Predictive AIOps What is likely to fail next? Only as good as the history it trained on; check the training window
Root-cause candidates Which alert is the cause vs the symptom? Depends on topology from Service Mapping and on correlation rules

Where “we get no ITOM data” actually comes from

  1. MID Server — check the ECC queue depth and MID health first. A saturated or unreachable MID drops events silently instead of erroring.
  2. Agent Client Collector — for hosts that cannot be probed, verify the agent is checking in before blaming the alert rule.
  3. Event rules / connector — a registered event with no matching rule looks identical to an event that never arrived.
  4. Correlation rules — these decide whether 400 alerts become 1 incident; tune here before touching dashboards.
